# 东京怪兽对战：规则与技术方案

> 规则基线：King of Tokyo 基础版英文规则书，2023-11 版。
> 本文只描述游戏机制。公开发布时应使用原创名称、美术、角色与卡牌文案，或先取得权利方授权。

## 1. 产品范围

首版目标：

- 2-6 名玩家通过浏览器游玩。
- 一名玩家在本机启动服务，其他玩家通过房间链接加入。
- 服务端权威判定，客户端不能自行修改骰子、生命、能量或牌库。
- 完整实现基础版流程、2 人推荐变体、5-6 人东京湾和基础牌效果。
- 支持断线重连、观战、房主重新开始和规则日志。
- 首版不做账号系统、匹配系统、扩展包、AI 和长期排行榜。

“本地起服务”有两种连接方式：

- 同一局域网：分享 `http://局域网IP:端口`，不依赖第三方服务。
- 异地联网：通过 Tailscale 私有网络，或 Cloudflare Tunnel 暴露 HTTPS 地址。仅启动本地服务并不能让公网玩家直接访问。

## 2. 基础规则

### 2.1 胜利条件

- 每名怪兽初始 10 点生命、0 点胜利分。
- 游戏在一个完整回合结束时检查胜利。
- 达到至少 20 分且仍存活者获胜；或仅剩一名怪兽存活时获胜。
- 若玩家在同一回合达到 20 分又降到 0 生命，该玩家被淘汰，不能获胜。
- 若所有怪兽同时被淘汰，则无人获胜。

### 2.2 开局

- 支持 2-6 人，座次固定，按顺时针行动。
- 2-4 人只使用东京城；5-6 人同时使用东京城和东京湾。
- 洗混牌库，翻开 3 张可购买卡牌。
- 所有人掷 6 颗基础骰，攻击结果最多者先手；平手者继续掷至决出先手。
- 开局东京为空。

### 2.3 回合阶段

一个回合严格分为：

1. 回合开始
2. 掷骰
3. 结算骰子
4. 进入东京
5. 购买卡牌
6. 回合结束

#### 回合开始

- 若当前玩家在东京，获得 2 分。
- 处理“回合开始时”卡牌效果与玩家选择。

#### 掷骰

- 默认使用 6 颗基础骰；卡牌可增减骰子或加入额外骰。
- 最多掷 3 次，也可提前停止。
- 第一次掷全部可用骰。
- 后续每次掷骰前，玩家可任意保留骰子，也可把之前保留的骰子重新加入。
- 最终结果必须全部结算。

#### 结算骰子

玩家可选择各类结果的结算顺序，但每颗骰子都必须被结算。

数字：

- 三个相同数字构成一组并获得该数字的分数。
- 同数字每多一颗，再加 1 分。
- 例：四个“2”获得 3 分。
- 三个或更多“1”结算时，在正常得分的同时提升 2 个等级；三个或更多“2”则在正常得分的同时提升 1 个等级，无需二选一。
- 怪兽初始为 0 级，达到或跨过 3、6、10 级时，从该等级的公共技能池中选择一个尚未被其他玩家取得的技能。
- 每个等级有 6 个效果不同的候选技能；本局技能池数量等于开局玩家数，最多 6 个，并在开局时随机抽取后固定。
- 同一个技能整局只能由一名玩家获得，先达到等级的玩家拥有优先选择权。
- 3、6、10 级技能强度逐级提高，10 级技能是难以取得但足以改变战局的终极进化。
- 已获得的进化技能与保留牌均为公开信息。

能量：

- 每个能量结果获得 1 点能量。
- 能量可跨回合保留，默认没有持有上限。

攻击：

- 每个攻击结果造成 1 点伤害。
- 攻击者在东京时，所有东京外怪兽各受到完整伤害。
- 攻击者在东京外时，东京城和东京湾中的所有怪兽各受到完整伤害。
- 同在东京的怪兽彼此不会被骰子攻击。
- 因其他玩家的攻击骰受伤后，东京内每名存活怪兽分别决定留下或撤离；伤害不会因撤离而取消。
- 卡牌造成的失血不等同于攻击骰伤害，不能借此撤离东京。
- 生命降至 0 时立即淘汰；弃掉其保留牌、标记和能量，并更新东京湾是否仍开放。

治疗：

- 东京外每个治疗结果恢复 1 点生命。
- 东京内不能用治疗骰恢复生命，但仍可通过卡牌恢复。
- 默认生命不能超过 10，除非保留牌明确提高上限。
- Poison、Shrink 等效果可能允许将治疗结果改作移除标记；这属于玩家选择。

#### 进入东京

- 结算骰子后，若当前启用的东京位置有空位，当前玩家必须进入。
- 存活人数 2-4：只启用东京城。
- 存活人数 5-6：东京城和东京湾均启用；优先填东京城，再填东京湾。
- 每次从东京外进入东京，立即获得 1 分。
- 若东京中的怪兽因本回合攻击撤离，攻击者在此阶段填补空位。
- 怪兽不能主动离开东京，只能在受到另一名怪兽的攻击骰伤害后选择撤离。

#### 购买卡牌

- 市场始终尽量保持 3 张正面朝上的牌。
- 玩家支付卡面能量费用购买任意张牌；每买一张立即补牌，新牌本回合也可继续购买。
- 玩家可支付 2 点能量弃掉市场全部 3 张牌并补充 3 张；能量足够时可重复刷新。
- `Discard` 牌购买后立即执行并进入弃牌堆。
- `Keep` 牌持续生效，直到被其他效果弃掉或游戏结束。
- 新牌翻开时，可能触发非当前玩家的购买窗口，例如 Opportunist；多个响应者按当前玩家之后的顺时针顺序获得机会。

#### 回合结束

- 依序处理“回合结束时”效果和选择。
- 检查当前玩家是否以至少 20 分存活，或场上是否只剩一个存活玩家。
- 若未结束，行动权交给下一名存活玩家。

### 2.4 双人推荐变体

其他规则不变，只调整东京奖励：

- 进入东京获得 1 点能量，而不是 1 分。
- 在东京开始回合获得 1 分，而不是 2 分。

房间设置应允许房主开启或关闭此变体，并在开局后锁定。

## 3. 必须明确的数字版裁定

实体桌游可以靠玩家协商，网游必须给出唯一结果：

- 随机数仅在服务端生成；每局记录随机种子和事件序号，方便复盘。
- 多个同时效果默认按当前玩家起顺时针顺序处理。
- 同一玩家有多个同优先级效果时，由该玩家选择顺序。
- 结算过程出现选择时，游戏进入 `pendingDecision`，其他非法指令全部拒绝。
- 每条指令带 `expectedRevision` 和唯一 `commandId`，避免重连或双击导致重复执行。
- 胜利通常在回合结束检查；死亡和东京湾关闭必须立即处理。
- 牌库耗尽时，将弃牌堆洗混成新牌库；若无牌可补，市场允许暂时少于 3 张。
- 玩家掉线不会停止房间状态；默认等待其重连，由房主选择延时、跳过或结束房间。竞技模式可另设回合计时器。

## 4. 首选技术方案

### 4.1 总体架构

采用 TypeScript 单仓库：

```text
apps/
  web/             React 浏览器客户端
  server/          Fastify HTTP + Socket.IO 房间服务
packages/
  game-engine/     纯函数规则引擎，不依赖网络和 UI
  protocol/        Zod 消息协议与共享类型
  content/         怪兽、卡牌和本地化数据
  ui/              可复用 UI 组件
tests/
  scenarios/       完整对局和卡牌组合测试
```

建议技术栈：

- 运行时：Node.js 24 LTS。当前机器的 Node.js 18 已停止维护，需要升级。
- 包管理：pnpm workspace。
- 前端：React + Vite + TypeScript。
- 服务端：Fastify + Socket.IO。
- 校验：Zod，客户端与服务端共用协议定义。
- 测试：Vitest 做规则单测和性质测试，Playwright 做多浏览器对局测试。
- 持久化：MVP 使用内存房间 + 可选 JSON 事件日志；需要跨重启恢复时再接 SQLite。
- 发布：单个 Docker 镜像，同时托管前端静态资源和 WebSocket 服务。

不建议直接采用 boardgame.io 作为核心规则层。它能处理普通回合制流程，但本游戏大量卡牌会引入跨玩家响应窗口和嵌套选择；自有的命令/事件状态机更容易精确表达、测试和回放。Socket.IO 只负责传输，不承载规则。

### 4.2 权威规则引擎

核心 API：

```ts
type Command = {
  id: string;
  roomId: string;
  playerId: string;
  expectedRevision: number;
  type: CommandType;
  payload: unknown;
};

type ReduceResult = {
  state: GameState;
  events: GameEvent[];
};

function dispatch(state: GameState, command: Command): ReduceResult;
```

要求：

- `dispatch` 是确定性的纯函数；随机结果通过显式 RNG 状态产生。
- 服务端验证行动玩家、阶段、资源、目标和版本号。
- 客户端只发送意图，例如 `ROLL_DICE`、`SET_ASIDE_DICE`、`YIELD_TOKYO`、`BUY_CARD`。
- 服务端广播脱敏后的状态视图；未来若加入隐藏信息，不必重写协议。
- 事件日志用于动画、规则说明、断线追赶和问题复现。

### 4.3 卡牌系统

不要把 60 多张牌写成散落的 `if/else`，也不要执行配置中的任意脚本。

采用“声明式效果 + 少量专用处理器”：

```ts
type Trigger =
  | "turn:start"
  | "dice:beforeRoll"
  | "dice:resolved"
  | "damage:dealt"
  | "card:revealed"
  | "turn:end";

type Effect =
  | { kind: "gain"; resource: "hp" | "energy" | "vp"; amount: number }
  | { kind: "damage"; target: TargetSelector; amount: number }
  | { kind: "modifyDiceCount"; amount: number }
  | { kind: "requestChoice"; choice: ChoiceDefinition }
  | { kind: "custom"; handler: CustomEffectId };
```

- 常见牌使用可校验的数据配置。
- Mimic、Metamorph、Opportunist 等例外牌使用白名单专用处理器。
- 每张牌至少有正常路径、资源不足、目标死亡、多人并发和复制效果测试。
- 卡牌名称、文案和插画与规则实现分离，便于替换成原创内容或授权内容。

### 4.4 联网与房间

房间生命周期：

```text
LOBBY -> STARTING -> PLAYING -> FINISHED -> CLOSED
```

- 创建房间后生成短房间码和邀请链接。
- 玩家以昵称加入，服务端签发不可猜测的重连令牌并保存在浏览器。
- 房主设置人数、双人变体、是否允许观战和回合计时。
- 开局后锁定座次和规则配置。
- 每个房间串行处理命令，避免两个 WebSocket 消息同时改状态。
- 定期发送完整快照，其余时间发送事件或状态差量。
- 重连时以最新快照和缺失事件恢复。
- 服务端不接受客户端提交的骰子结果、抽牌结果或完整状态。

### 4.5 安全边界

- 所有 Socket.IO payload 都经过 Zod 校验，并限制大小和发送频率。
- 昵称、聊天和房间名做长度限制与转义。
- 房间码只用于定位；玩家身份使用高熵令牌。
- 公网模式必须使用 HTTPS/WSS。
- 不在日志中记录重连令牌。
- 首版不收集邮箱、密码等个人数据。

## 5. 数据模型要点

`GameState` 至少包含：

- `revision`、`status`、`ruleset`、`rngState`
- 玩家顺序、当前玩家、每位玩家的生命/分数/能量/存活状态
- 东京城与东京湾占用者
- 当前阶段、掷骰次数、全部骰子及保留状态
- 牌库、弃牌堆、市场、每名玩家的保留牌和标记
- 当前待决策项及合法响应者
- 最近事件和胜利结果

服务端另存不对玩家广播的：

- 房间管理令牌
- 玩家重连令牌哈希
- Socket 与玩家映射
- 连接状态和超时信息

## 6. 测试策略

规则引擎是项目的主要风险，测试优先于动画：

- 单元测试：每种骰面、东京进出、伤害、治疗、死亡、胜利。
- 表驱动测试：2-6 人的东京槽位与东京湾关闭。
- 卡牌契约测试：每张牌至少一组独立场景。
- 性质测试：生命/能量不越界、死亡玩家不行动、修订号单调增长、同种子同命令得到同结果。
- 回放测试：事件日志重放后的状态与实时状态一致。
- 协议测试：伪造身份、过期 revision、重复 commandId、非法阶段均被拒绝。
- Playwright：启动 2-6 个浏览器上下文，覆盖建房、加入、整局、掉线重连。

首批验收场景：

1. 首位玩家无目标可攻击，随后必须进入东京并得分。
2. 东京怪兽受攻击后分别选择留下或撤离。
3. 五人局两处东京均被攻击；减员至四人时东京湾立即关闭。
4. 双人变体正确替换两项东京奖励。
5. 玩家同回合达到 20 分并死亡时不能获胜。
6. 两名玩家被同一攻击同时淘汰后正确判断最后幸存者或无人获胜。
7. 买牌后立即补牌，Opportunist 在正确的响应顺序中插入。
8. 断线重连不会重复掷骰、扣能量或执行卡牌。

## 7. 开发分期

### 里程碑 A：可玩的无卡牌核心

- 工程骨架、房间大厅、2-6 人加入。
- 掷骰三次、保留骰子、数字/能量/攻击/治疗。
- 东京城/东京湾、撤离、淘汰、胜利。
- 断线重连和完整规则日志。

### 里程碑 B：完整基础牌

- 市场、购买、刷新、牌库与弃牌堆。
- 效果触发器、待决策队列、标记和额外骰。
- 逐张实现并测试基础牌。

### 里程碑 C：体验与部署

- 响应式桌面、骰子与伤害动画、音效开关。
- 观战、房主控制、回合计时与 AFK 处理。
- Docker、一键启动脚本、局域网地址提示、Tailscale/隧道说明。

### 里程碑 D：后续能力

- SQLite 对局恢复与战绩。
- 原创内容编辑器。
- AI 玩家。
- 扩展包规则模块。

## 8. 结论

首选方案是 React + Fastify + Socket.IO + 独立 TypeScript 规则引擎。先完成不含卡牌但覆盖所有基础骰子与东京规则的纵向切片，再实现卡牌事件系统。这样最快得到一局真正可联机、可重连、可验证的游戏，同时不会让复杂卡牌把网络层和 UI 一起拖入难以测试的状态。
